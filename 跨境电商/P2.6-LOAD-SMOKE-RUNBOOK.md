# Cross-Border E-Commerce P2.6 Load-Smoke Runbook

This runbook operationalizes `PHASE-2.md §9` for the mobile-accessory Cross-border e-commerce / 跨境电商 pilot. It verifies multi-user readiness, workload backpressure, backup/restore mechanics, and production-readiness evidence without building a custom runtime or bypassing OpenClaw.

## Scope

The P2.6 smoke is a controlled readiness drill, not a full paid-provider soak:

- Seed 50 temporary `operator` users under tenant `cross-border-ecommerce`.
- Simulate 50 Dashboard sessions through the typed CBE tenant-context boundary.
- Create 10 Lead `find-10` requests with 3 exact duplicate scopes and 2 near-duplicate scopes.
- Create 5 Screening batches with 25 total targets; verify parent tasks plus single-target child runs and queue overflow.
- Create 3 Accio imports with redacted fixture payloads.
- Run a DB-only C=40/48 pressure profile that verifies excess work queues at the 24 soft cap and the 32 hard cap guard.
- Record p95 Dashboard API latency plus load-smoke audit/cost-ledger metadata.
- Mark the local DB-only result as `db_only_preflight_passed`; reserve `production_go_live_ready` for the same checks on the actual target deployment plus target restore drill and provider headroom review.

The live script does not start real OpenClaw AgentChat sessions and does not call Google Maps, Companies House, SEC, RDAP, Hunter, Abstract, ImportYeti, Volza, or LLM providers. It creates and cleans up DB probe rows through the existing typed store and direct migration-safe SQL only.

## Commands

Static contract check:

```bash
pnpm exec tsx scripts/test-cross-border-phase2-load-smoke.ts
```

Live PostgreSQL load-smoke check:

```bash
set -a
source sentura/dashboard/.env.local
set +a
pnpm exec tsx scripts/test-cross-border-phase2-load-smoke.ts --require-db --report outputs/cbe-phase2-load-smoke-report.json
```

Expected result:

- 50 probe users and profiles are created, resolved, and cleaned up.
- Lead exact duplicates join one active run; near duplicates offer choices.
- Screening creates 5 parent runs and 25 child runs; no child carries more than one target.
- With default caps, 12 Screening children run and at least 13 queue before any drain.
- A failed child releases one slot and a queued child can be claimed; the failed child is retryable without rerunning siblings.
- Accio admits 3 imports.
- C=48 DB-only pressure keeps active count at the 24 soft cap and queues excess requests.
- A separate DB-only hard-guard probe verifies new work queues when 32 active slots already exist.
- `api_call_ledger` rows are attributable to `agent_run_id`.
- `audit_events` contains the load-smoke report with p95 latency and `go_live_readiness = "db_only_preflight_passed"`.

## Backup/Restore Drill

Use a disposable restore database. Never restore into the source database.

```bash
set -a
source sentura/dashboard/.env.local
set +a
export CBE_RESTORE_DATABASE_URL="postgresql://postgres:postgres@localhost:5432/sentura_cbe_restore_drill"
# Optional when local pg_dump/pg_restore are unavailable or older than the source server:
# export CBE_POSTGRES_CLIENT_IMAGE="postgres:18"
bash scripts/cross-border-phase2-backup-restore-drill.sh
```

The script runs:

- `pg_dump --format=custom --no-owner --no-privileges` against `CBE_DATABASE_URL`.
- `pg_restore --clean --if-exists --no-owner --no-privileges` into `CBE_RESTORE_DATABASE_URL`.
- `pnpm exec tsx sentura/lib/cross-border-store/migrate.ts --seed` against the restored database.
- `pnpm exec tsx scripts/test-cross-border-phase2-store.ts --require-db` against the restored database.

Safety guards:

- `CBE_RESTORE_DATABASE_URL` is required.
- Source and restore URLs must differ.
- The restore URL must contain `restore` or `drill`, unless `CBE_ALLOW_NON_RESTORE_TARGET=1` is deliberately set for a known disposable database.
- When `CBE_POSTGRES_CLIENT_IMAGE` is set, the script runs `pg_dump` / `pg_restore` from that Docker image and rewrites local PostgreSQL hosts to `host.docker.internal` for container access.

## Production-Readiness Checklist

The local DB-only preflight can be labeled `db_only_preflight_passed` after the commands above pass. A target deployment can only be labeled `production_go_live_ready` when these are all true:

- `scripts/test-cross-border-phase2-load-smoke.ts --require-db` passes on the target deployment profile.
- `scripts/cross-border-phase2-backup-restore-drill.sh` passes against a disposable restore database in the target environment.
- `pnpm exec tsx scripts/test-cross-border-phase2-concurrency.ts --require-db` passes.
- `pnpm exec tsx scripts/test-cross-border-phase2-store.ts --require-db` passes.
- `pnpm --dir sentura/dashboard exec tsc --noEmit` passes.
- `pnpm --dir sentura/dashboard build` passes for the target environment.
- CE22/P2.5 paid email/trade retry state, durable Screening retry/recovery, Accio approval-to-memory promotion, and durable Screening handoff consumption remain green in `scripts/test-cross-border-phase2-store.ts --require-db`.
- Target deployment confirms provider quota headroom, model concurrency, DB connection limits, Gateway RSS behavior, and source-specific rate limits.

## Result Labels

Use these labels in handoff and test logs:

| Label | Meaning |
|---|---|
| `static_contract` | Static script/docs/config checks only. |
| `db_only_load_smoke` | Live PostgreSQL typed-store smoke; no real OpenClaw sessions or external providers. |
| `db_only_preflight_passed` | DB-only load smoke plus local store/concurrency/type/build checks passed; target deployment remains separate. Include `backup_restore_drill = "passed"` in the JSON report when the local restore drill has also run. |
| `target_deployment_load_smoke` | Same workload on the target deployment with Dashboard/Gateway processes running. |
| `provider_soak` | Explicitly approved run that allows real provider/API traffic and measured costs. |
| `production_go_live_ready` | Target deployment smoke, target backup/restore drill, store/concurrency/type/build checks, and provider quota review all passed. |

Do not label any local DB-only result `production_go_live_ready`; use that label only after the target deployment checklist passes.
