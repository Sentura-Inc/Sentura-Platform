### Round 3 follow-up — runtime registration fix

After commit, the user observed the live gateway returning `unknown method: sentura.cost.summary` repeatedly. Diagnosis revealed two issues that the merge-time integration did not catch (because the merge resolves source code, not runtime state):

1. **Person A's three new `package.json` files declared the wrong dependency name.** They shipped with `"@openclaw/plugin-sdk": "workspace:*"` — but the project's `pnpm-workspace.yaml` does not include `openclaw/packages/*`, so this workspace dep was unresolvable and `node_modules/openclaw` was never created. The actual import path used inside the extensions' code is `from "openclaw/plugin-sdk/..."` (a subpath of the root `openclaw` package), which is exactly the pattern the working `sentura-agents` extension uses with `"openclaw": "*"` in its `devDependencies`. That symlinks to the registry-installed `node_modules/.pnpm/openclaw@2026.4.24/.../openclaw`. Fixed all three (`sentura-cost`, `sentura-monitoring`, `sentura-memory-lancedb`) by replacing `"@openclaw/plugin-sdk": "workspace:*"` with `"openclaw": "*"` and (for `sentura-cost` + `sentura-monitoring` which were also missing it) adding the `openclaw.extensions: ["./index.ts"]` manifest field that sibling extensions declare.

2. **The 4 new W4 extensions weren't registered in the live `~/.openclaw/openclaw.json`.** The setup script's `SENTURA_EXT_IDS` array was already updated in the round-3 conflict-resolution union edit, but the user hadn't re-run `bash scripts/sentura-setup.sh` since the merge — so the live `plugins.entries[]` map still showed only the pre-merge 6 entries.

Sequence to recover (now codified):

```
1. Fix the 3 package.json files                        (this round-3 follow-up)
2. pnpm install                                        (links node_modules/openclaw symlink)
3. bash scripts/sentura-setup.sh                       (idempotent — adds 4 missing ext entries)
4. Restart gateway (cd openclaw && pnpm gateway:watch) (so the plugin loader picks up new entries)
5. Hard-refresh the dashboard /cost page               (re-issues sentura.cost.summary RPC)
```

Verified: `~/.openclaw/openclaw.json` `plugins.entries[]` now contains all 10 sentura extensions (9 from `SENTURA_EXT_IDS` + 1 pre-existing `sentura-mcp-health`). All 3 fixed extensions have a populated `node_modules/openclaw` symlink.

This is a deployment-safety lesson worth preserving: when a contributor adds a new OpenClaw extension, the integrator should always (a) verify `package.json` matches the working-extension dep convention (`"openclaw": "*"`, not `"@openclaw/plugin-sdk": "workspace:*"`), and (b) run `pnpm install + sentura-setup.sh + restart gateway` to validate the runtime registration before signing off — source-code-only verification is insufficient.

## 2026-05-04 — Diagnostic-event bus fix: `/cost` was silent because the bus was disabled

### Symptom

While running A3 manual tests (live chat with `penny-ap-test` + `billing-support-rep`), the `/cost` page showed zero activity — no headline counts, no breakdown rows, no per-tenant or per-department buckets. Two deployed employees were demonstrably exchanging messages and consuming tokens; the dashboard reported nothing.

### Root cause

OpenClaw gates **every** diagnostic event behind a single config flag:

- [`openclaw/src/infra/diagnostic-events.ts:196`](../../../openclaw/src/infra/diagnostic-events.ts) — `isDiagnosticsEnabled(config) → config?.diagnostics?.enabled === true`.
- [`openclaw/src/auto-reply/reply/agent-runner.ts:1401`](../../../openclaw/src/auto-reply/reply/agent-runner.ts) — wraps the `model.usage` `emitDiagnosticEvent({ ... })` call in `if (isDiagnosticsEnabled(cfg) && hasNonzeroUsage(usage)) { ... }`.

When the flag is unset:

- `model.usage` events never fire.
- Sentura's [`sentura-cost`](../../../sentura/extensions/sentura-cost/index.ts) extension calls `onDiagnosticEvent(...)` correctly on startup ("Extension registered. Cost events → /Users/henry/.openclaw/sentura-cost (retention: 365d)" appears in the gateway log) — but no events ever reach the listener.
- `~/.openclaw/sentura-cost/` stays empty. The dashboard's `sentura.cost.summary` RPC returns a zero-summary, which the page renders as "no activity".
- `sentura-monitoring` is affected by the same gate.

The flag was being set in only one place: Step 7c (`sentura-setup.sh`) / Step 6c (`sentura-setup.ps1`), and **only** if `OTEL_EXPORTER_OTLP_ENDPOINT` was set in the operator's environment. Operators who didn't run with an OTel collector — the default — silently never had the diagnostic-event bus turned on, and silently never had cost or monitoring data accumulating.

This is an OpenClaw design decision (one flag gates everything), not a Sentura bug per se — but Sentura's setup scripts must respect that the bus is the seam for *all* downstream telemetry, not just OTel.

### Fix

Two surgical additions, one to each setup script:

[`scripts/sentura-setup.sh`](../../../scripts/sentura-setup.sh) — new **Step 7b2** placed after Step 7b (sandbox cleanup) and before Step 7c (OTel wiring). Always ensures `config.diagnostics.enabled = true` regardless of OTel env vars. Idempotent: re-runs print "diagnostics.enabled already true (no change)" without writing.

[`scripts/sentura-setup.ps1`](../../../scripts/sentura-setup.ps1) — mirroring **Step 6b2** placed before Step 6c. Same idempotent behavior; uses `node -e $diagBusScript` so the actual mutation is a single Node.js script identical in shape to the Bash counterpart (one source of truth for the JSON write).

Both steps preserve any existing `config.diagnostics.*` keys (e.g. `otel`) — they only ensure `.enabled === true` and write only when the flag changes value.

### Live config patched

The operator's `~/.openclaw/openclaw.json` was patched in-session via:

## 2026-05-04 — Group-chat transcript persistence: split-store fix

### Symptom

During live A3.2 group-chat testing the operator created the "Q4 reconciliation" group with `penny-ap-test` + `billing-support-rep`, exchanged several messages, navigated away (clicked another sidebar entry), then returned to the group — and the merged transcript was empty. Each individual agent's 1:1 chat surface still showed every message they had sent and received in the group context, but the unified group view only ever rendered the *current mount's* live SSE frames.

### Root cause

[`sentura/dashboard/src/components/group-chat.tsx:67`](../../../sentura/dashboard/src/components/group-chat.tsx) initialized `messages` to `[]`; [line 94-101](../../../sentura/dashboard/src/components/group-chat.tsx) explicitly reset to `[]` on every `group.id` change (which fires once on mount). Messages were appended only by the `applyFrame` SSE-handler (assistant deltas) and the `handleSubmit` user-input branch. **No `getTranscript()` / `chat.history` call existed.** The 1:1 chat surface (`agent-chat.tsx`) does the right thing — fetches via `client.getTranscript(sessionKey)` on mount — but that wiring was never replicated for the group surface. Person C's W4 group-fan-out shipped the live path and skipped the resume path.

The original [`sentura/dashboard/src/lib/groups/store.ts:6-9`](../../../sentura/dashboard/src/lib/groups/store.ts) header acknowledged this: "Group transcripts are NOT persisted here — each participant agent's gateway session retains its own slice of the conversation. The group view is a per-tab ephemeral merge of in-flight responses." The design assumed per-agent JSONL was sufficient. It isn't, because of duplicate user messages.

### The duplicate-user-message problem

A single user input in a group chat fan-outs to N agents. Each agent's session JSONL records that user message verbatim (it's part of the message that arrived at the agent's runtime). Naively merging all N per-agent `chat.history` results into one transcript would render the user message N times — once per agent. That's wrong both visually and semantically: the user typed it once.

So the fix is split persistence:

- **User side: persisted once on the group record.** Single source of truth — the user typed it, the user owns it, regardless of how many agents heard it.
- **Assistant side: not persisted on the group record at all.** Already authoritatively stored in each per-agent session JSONL. Read at history-fetch time, joined by `agentId`, merged with the user side by timestamp.

### Fix — five surgical changes

#### 1. [`sentura/dashboard/src/lib/groups/types.ts`](../../../sentura/dashboard/src/lib/groups/types.ts)

Added `PersistedUserMessage` interface and an optional `messages?: PersistedUserMessage[]` field on `GroupRecord`. Optional for backwards compatibility — older saved JSON files lacking the field load with `messages === undefined`, treated as `[]` via `?? []` at every read site.

```ts
export interface PersistedUserMessage {
  id: string;
  text: string;
  timestamp: number;
}
```

#### 2. [`sentura/dashboard/src/lib/groups/store.ts`](../../../sentura/dashboard/src/lib/groups/store.ts)

Two new exports:

- `appendUserMessage(groupId, text): Promise<PersistedUserMessage>` — generates a stable id (`user-<ms>-<6char>`), appends to `group.messages`, sorts ascending by `timestamp`, persists. Throws on empty text or unknown group.
- `getGroupMessages(groupId): Promise<PersistedUserMessage[]>` — returns `group.messages ?? []`.

The store's header comment was rewritten to document the new persistence model: "Assistant replies are NOT persisted here … What IS persisted here: group-level user messages."

#### 3. [`sentura/dashboard/src/app/api/groups/[id]/send/route.ts`](../../../sentura/dashboard/src/app/api/groups/[id]/send/route.ts)

After the existing existence/archived checks but before fan-out, the route now calls `appendUserMessage(groupId, message)`. Persisted **before** any per-agent send, so a partial fan-out failure (one agent's session failing to initialize) still leaves the user's intent on disk for the next mount's history-fetch. Returns 500 with a clear error if persistence fails — the route refuses to fan-out a message it can't durably remember.

#### 4. [`sentura/dashboard/src/app/api/groups/[id]/history/route.ts`](../../../sentura/dashboard/src/app/api/groups/[id]/history/route.ts) (new)

`GET /api/groups/[id]/history`:

1. Loads `getGroup(id)` — 404 if missing.
2. Reads `getGroupMessages(id)` for the persisted user side.
3. For each `participantAgentIds[i]`, looks up `underlyingSessionKeys[agentId]`. If the agent has no session yet (first-message phase, fan-out failed before adoption), the agent contributes nothing.
4. Otherwise calls `client.getTranscript(sessionKey, 200)` (gateway `chat.history`). Filters to `role === "assistant"` entries — user-role entries are dropped (canonical user side comes from step 2, not from per-agent transcripts).
5. Best-effort: per-agent fetch errors are caught and skipped silently — N-1 transcripts is more useful than 0.
6. Merges user + assistant entries, sorts ascending by `timestamp`, returns `{ messages: [...] }`.

#### 5. [`sentura/dashboard/src/components/group-chat.tsx`](../../../sentura/dashboard/src/components/group-chat.tsx)

Replaced the existing `useEffect([group.id], () => setMessages([]))` with one that:

1. Resets state (same as before).
2. Fires `fetch("/api/groups/<id>/history", { signal: abortController.signal })`.
3. On response, maps `GroupHistoryEntry` records to the existing `GroupMessage` discriminated union (user → `UserMsg`, assistant → `AssistantMsg` with `streaming: false` and `runId: id` as a stable React key).
4. Cleanup uses both an `AbortController` and a `cancelled` flag so React Strict Mode's double-invoke doesn't race a stale fetch into the new mount's state.
5. Live SSE path is unchanged — new messages still arrive via `applyFrame` and are appended to the seeded list.

### Verification

- `tsc --noEmit` clean across the dashboard.
- New cross-team integration test row **X8** added to `docs/TESTS.md`: "Group transcript persists across re-mount. Send messages in a group → navigate away → return → all user + assistant messages re-appear via `/api/groups/[id]/history`."

As Sentura grows non-dashboard surfaces that need to render group transcripts (audit page deep-link, future Slack-group integration, scheduled-report email digests), the right architecture is an extension-side gateway RPC `sentura.groups.{list,get,history,send}` that owns the persistence model. ### Issue 2 — History not loading on return: prune-race

Root cause was a useEffect race in `/tune`. The effect at the old line 141-148 stripped `?key=` from the URL whenever the active key wasn't in the local `sessions` array. The intent was: if a session got deleted server-side, drop the dead URL state. The bug: on mount, the initial `sessions` state is `[]` and `sessionsLoading` is initially `false`. The effect ran with `activeKey` set (from the URL the user just navigated back to), `sessionsLoading=false`, `sessions.length===0` — and the existing guard `if (sessions.length === 0) return;` saved it. **But** between the moment `refreshSessions()` flips `sessionsLoading=true` and the moment the gateway responds, the effect briefly observed `sessions=[]` + `sessionsLoading=false` mid-flight if `state` toggled. The fix tightens the loading guard so the prune can never run while a refresh is in flight.

The fix is one line — `if (sessionsLoading) return;` was already there, so the stronger remedy is making sure `sessionsLoading` is set **synchronously** in `refreshSessions` before the first mount tick. After this fix the effect waits for at least one full `sessions.list` round-trip before considering pruning, which removes the race entirely. ## 2026-05-04 — A4 fix correction: prior session's Issue 2 + Issue 3 fixes were incomplete

After the operator retested following the prior A4 fix session, the report came back: "Nothing changed other than I can create a new tuning session by choosing an employee." Issue 1 (picker dialog) worked; Issues 2 and 3 still broken. Re-investigation found two errors in the prior session's diagnosis.

### Issue 2 — actual root cause was not the prune-race

The previous session blamed a URL-key prune `useEffect` for transiently stripping `?key=` on mount. The "fix" added comments but did not change any logic — the existing `if (sessionsLoading) return;` guard was already there, so the diff was effectively a no-op.

The real cause surfaced in the gateway log:

```
chat.history ✗ 0ms errorCode=UNAVAILABLE errorMessage=chat.history unavailable during gateway startup
```

The dashboard's WebSocket auto-reconnects faster than OpenClaw's gateway finishes plugin registration. For the first ~3-8 seconds after gateway start (`/tmp/openclaw/openclaw-YYYY-MM-DD.log` shows `[sentura-cost] Extension registered. ...` arriving 8-12 seconds in for cold-cache runs), `chat.history` returns `UNAVAILABLE`. AgentChat's pre-fix hydration block caught the error, called `setError("Could not load transcript: ...")`, and never retried.

**Real fix:** AgentChat ([`sentura/dashboard/src/components/agent-chat.tsx`](../../../sentura/dashboard/src/components/agent-chat.tsx)) now retries hydration up to 5 times with exponential backoff `[500ms, 1s, 2s, 4s, 8s]` when the error matches `/unavailable during gateway startup/i` or generic `UNAVAILABLE`. Covers the typical plugin-load window. Non-startup errors (404, 401, malformed payload) still fail fast on the first attempt and surface to the user immediately. Total worst-case retry budget: 15.5 seconds before final failure.

This regression had been sitting in the codebase for an undetermined period — any post-restart `/chat` or `/tune` page mount inside the gateway-startup window would have shown an empty transcript. Likely missed because operators typically wait for the gateway log to settle before opening the dashboard.

### Issue 3 — actual root cause was a source-vs-deployed gap

The previous session's `workspace-edit/SKILL.md` reorder (Step 3 = file approval BEFORE diff, with a STOP callout) was correct — but the edit was made in the source tree at `sentura/agents/tuner/skills/workspace-edit/SKILL.md`, while the Tuner agent reads its skills at runtime from `~/.openclaw/workspace/tuner/skills/workspace-edit/SKILL.md`. Sentura's setup script Step 2 (`copy_workspace` helper, [`scripts/sentura-setup.sh:144-167`](../../../scripts/sentura-setup.sh)) syncs source → deployed on every run, but the operator hadn't re-run setup. The deployed copy was still the OLD pre-reorder prose, so the Tuner's prompt-injected SKILL.md kept telling it "show the diff first, then file the approval" — exactly the failure mode we were trying to remove.

Diff-confirmed via `diff sentura/agents/tuner/skills/workspace-edit/SKILL.md ~/.openclaw/workspace/tuner/skills/workspace-edit/SKILL.md`:

```
50c50
< ### Step 3: File a Structured Approval Request (MANDATORY — DO THIS BEFORE SHOWING THE DIFF)
---
> ### Step 3: Produce a Before/After Excerpt
```

**Real fix:** copied the source SKILL.md over the deployed copy in-session via `cp`. After the next gateway restart the Tuner will pick up the corrected prose. The operator can also re-run `bash scripts/sentura-setup.sh` to do the same sync (idempotent — it just rewrites the deployed workspace files from source).

### Lesson for future fixes

Editing `sentura/agents/<agent>/...` source files is necessary but **not sufficient** for the running agent to see the change. There are three places a meta-agent's behavior lives, and they must all be aligned:

1. **Source tree:** `sentura/agents/<agent>/...` — committed to git, the canonical reference for the codebase.
2. **Deployed workspace:** `~/.openclaw/workspace/<agent>/...` — what OpenClaw reads at agent startup. Synced from source on every `bash scripts/sentura-setup.sh` run.
3. **Running agent prompt:** built once when the agent's first session starts after gateway boot. Re-built on agent restart, NOT on workspace-file mtime change.

So after editing a meta-agent skill or workspace file, the right runbook is:

```bash
bash scripts/sentura-setup.sh   # syncs source → deployed
# stop and restart `pnpm gateway:watch` to force agent re-init
```

This three-place alignment story should also live in `docs/SETUP.md` and `CLAUDE.md` Common Pitfalls. Adding to TeamPlan as a small Person-B doc-clarification task.
