# Sentura Development Memory

> ## ⚠️ Historical log — do NOT treat as specification ⚠️
>
> This file is an **append-only audit log** of development sessions, reorganized on 2026-04-19 into a **table of contents** that points at per-person / per-week detail files under `docs/memory/`. Older entries describe designs that have since been superseded. In particular, anything in the detail files that mentions `RULES.md` or `CONTEXT.md` as real workspace files is **historical only** — those files were fully removed on 2026-04-17 and must not be reintroduced.
>
> **Current policy** (authoritative sources: `.cursorrules` and `docs/TeamPlan.md`):
> - Sentura agent workspaces use exactly the 8 OpenClaw-native files.
> - Hard safety boundaries live inside `AGENTS.md → ## Hard Rules (must not override)`.
> - Enterprise context lives inside `BOOTSTRAP.md → ## Enterprise Context`.
> - The `sentura-bootstrap` hook injects only per-user memory (`memory/users/MEMORY_USER_{token}.md`).
>
> If anything in the detail files contradicts the current policy, the current policy wins. Do not mine `docs/memory/**` for requirements.
>
> **Structure.** `docs/MEMORY.md` is the matrix. Session prose and decision records live in:
> - `docs/memory/person-{a,b,c,d}/week-{N}.md` — per-owner, per-week
> - `docs/memory/shared/*.md` — cross-cutting sessions (architecture pivots, workspace collapses, multi-round bug hunts)
> - `docs/memory/sitlink/*.md` — independent Sitlink / 座联互动 project memory, outside the A/B/C/D sprint plan
> - `docs/memory/cross-border-ecommerce/*.md` — independent Cross-border e-commerce / 跨境电商 project memory, outside the A/B/C/D sprint plan
>
> **How to use this file.** Find the row for your task's area/week, open the linked detail file, read only the sections you need. The matrix is cheap to skim; the details are on-demand.
>
> **Continuation fast path.** If the user is continuing unfinished work, read only `outputs/task_handoff.md` first, especially its `Current Resume Snapshot` and `Next Steps`. Use this matrix for targeted lookup only when the handoff names a specific prior project-memory row, section, or detail to check.
>
> **Writing policy.** Add new sessions as a new row in the matrix **and** a new section in the appropriate detail file (create a new `week-N.md` if crossing into a new sprint week). For Sitlink work, use Owner `sitlink` and a detail file under `docs/memory/sitlink/` instead of a TeamPlan week. For Cross-border e-commerce work, use Owner `cross-border-ecommerce` and a detail file under `docs/memory/cross-border-ecommerce/` instead of a TeamPlan week. Never delete prior rows; summaries are allowed, but every session date, decision, file path, and fix must remain traceable from the matrix.

Servers spawn with `command: "node"` against their compiled `dist/index.js` rather than routing through `pnpm --filter`.

Runtime: Node **24 recommended**, 22.19+ supported (`engines: ">=22.19.0"`), package manager pnpm **11.2.2+**. Sentura imports must always come from current `openclaw/plugin-sdk/...` root-package subpath exports, **never** from `openclaw/src/plugin-sdk/` or `openclaw/packages/plugin-sdk/src/` directly. Removed `2026.6.x` convenience subpaths include `openclaw/plugin-sdk/diagnostics-otel` and `openclaw/plugin-sdk/memory-lancedb`; use `openclaw/plugin-sdk/diagnostic-runtime`, `openclaw/plugin-sdk/plugin-entry`, and `openclaw/plugin-sdk/state-paths` instead.

- **Setup bootstraps the first `platform_admin` automatically.** `scripts/sentura-setup.{sh,ps1}` seed a `platform_admin` into `~/.openclaw/sentura-rbac/users.json` and write `NEXT_PUBLIC_SENTURA_ADMIN_USER_ID` + `NEXT_PUBLIC_SENTURA_ADMIN_TOKEN` into `sentura/dashboard/.env.local` on every run. Customers never see `curl` or `sentura.rbac.users.upsert` during onboarding. Seeding is idempotent (existing admin wins — env-var changes do not silently rotate the token). The `withRbac` bootstrap escape hatch self-closes the moment the first admin lands, so fresh installs leave bootstrap mode on the first setup run. See `docs/SETUP.md → Platform admin bootstrap (auto-seeded, no curl required)` for env-var overrides and the manual token-rotation recipe.
- **Meta-agent workspace bootstrap is stamped, not deleted.** OpenClaw's `resolveWorkspaceBootstrapStatus` (`openclaw/src/agents/workspace.ts`) marks a workspace pending while `BOOTSTRAP.md` exists and `.openclaw/workspace-state.json` lacks a non-empty `setupCompletedAt`. While pending, non-primary runs (dashboard-spawned sessions) are forced into limited mode — which makes Forge refuse to deploy employees from the dashboard. Sentura keeps `BOOTSTRAP.md` permanently (it hosts `## Enterprise Context`), so `scripts/sentura-setup.{sh,ps1}` stamp `setupCompletedAt` into each meta-agent's state file (`creator`, `tuner`, `orchestrator`) after setup. Idempotent (existing timestamps are preserved). This is Sentura's deliberate divergence from OpenClaw's "delete `BOOTSTRAP.md` on first run" convention. See `docs/SETUP.md → Meta-agent bootstrap convention`, `docs/workspace-convention.md §7`, and `docs/OPENCLAW.md §4`.
- **In-process employee registration (post-2026-04-19 pairing fix).** Gateway RPCs that mutate config (`config.patch`, `agents.create`) require `operator.admin` scope, and OpenClaw's ws-connection message-handler hard-codes `silent=false` for scope upgrades — meaning a manual pairing approval is required. Forge (running inside the embedded agent runtime) has no way to click "approve" on its own pairing prompt, so `gateway.call("config.patch", …)` deadlocks forever with `GatewayClientRequestError: pairing required`. The fix is to route agent-registration writes through the `sentura-agents` extension's in-process API: `sentura_agents_manage { action: "register_agent", ... }` calls `api.runtime.config.{loadConfig, writeConfigFile}` directly (trusted-native, no gateway auth, no pairing), atomically appends the agent to `agents.list`, optionally appends channel `bindings[]` and `mcp.servers`, and stamps `setupCompletedAt` on the new workspace. `create_agent` now auto-stamps the setup state so a fresh employee is not bootstrap-pending. Forge MUST use `sentura_agents_manage` (not `gateway.config.patch`) for deploy-time config writes. See `sentura/extensions/sentura-agents/src/register-agent.ts` and the Creator's `skills/employee-deployment/SKILL.md` / `skills/incubation/SKILL.md` / `skills/workspace-generation/SKILL.md` / `TOOLS.md`.
- **Workspace bootstrap files have a hard 12,000-char injection limit.** OpenClaw's embedded agent runtime truncates `AGENTS.md` (and likely other workspace bootstrap files) when injecting them into the agent's system prompt — the log line to watch for is `agent/embedded: workspace bootstrap file AGENTS.md is <N> chars (limit 12000); truncating in injected context`. If a meta-agent's `AGENTS.md` grows past 12k, critical instructions at the bottom of the file are silently dropped from the agent's context and the agent will behave as if they don't exist (e.g. Forge refusing to call `sentura_agents_manage` because the Phase 5 "Deploy & Go Live" section got truncated). Keep `AGENTS.md` lean — push long-form narrative into skill files instead. Verified on 2026-04-19 after the Creator's AGENTS.md ballooned to 18,597 chars; shrank to ~11k to stay well under the limit.
- **Sandbox tool-policy filter for meta-agents (post-Round 20, 2026-04-19).** OpenClaw's sandbox defines a **separate** tool-allowlist layer in `openclaw/src/agents/sandbox/constants.ts` — `DEFAULT_TOOL_ALLOW` (narrow: `exec`, `process`, `read`, `write`, `edit`, `apply_patch`, `image`, `sessions_*`, `session_status`, `subagents`) and `DEFAULT_TOOL_DENY` (blocks `browser`, `canvas`, `nodes`, `cron`, `gateway`, and every channel id). This filter runs **after** the top-level `tools.allow` / `tools.alsoAllow` filter inside `applyToolPolicyPipeline` (step label `sandbox tools.allow`). Agent-level `tools.alsoAllow` does NOT bleed into this layer — a separate `tools.sandbox.tools.alsoAllow` block is required. Meta-agents (Forge, Tuner, Orchestrator, MCP Builder) MUST set `tools.sandbox.tools.alsoAllow` in their `config.json5` to expose plugin tools (`sentura_agents_manage`, `gateway`, `browser`, `pdf`, `canvas`, `cron`, `memory_search`, `memory_get`, `update_plan`, `image_generate`, `video_generate`, `web_fetch`, `web_search`, `sentura_rbac_manage`, `sentura_audit_query`). Channel-like entries listed in sandbox `alsoAllow` are auto-removed from `DEFAULT_TOOL_DENY` by `filterDefaultDenyForExplicitAllows` — no deny-list edit needed. **All four meta-agent source configs now ship with this block** (`sentura/agents/{creator,tuner,orchestrator,mcp-builder}/config.json5`), **and the setup scripts `scripts/sentura-setup.sh` / `scripts/sentura-setup.ps1` inject the same block into `~/.openclaw/openclaw.json` on every run** (idempotent) — so fresh installs and re-runs preserve the fix. Two probe scripts exist to verify: `scripts/probe-creator-tools.ts` (gateway `tools.effective`) and `scripts/probe-chat-send.ts` (runner debug, gateway `chat.send` path, reads `/tmp/openclaw/openclaw-YYYY-MM-DD.log`). Both must show `sentura_agents_manage` for the deploy pipeline to work from the dashboard. **Dashboard-vs-CLI distinction is important:** CLI (`openclaw agent --agent <id>`) and the `tools.effective` gateway RPC both report the pre-sandbox view and will happily show 21 tools even when the dashboard is seeing 7; always verify via `chat.send` (or `scripts/probe-chat-send.ts`) before declaring a sandboxed agent correct. Full narrative docs: `docs/SETUP.md` § "Sandbox tool-policy filter" (operational), `docs/OPENCLAW.md` § "Sandbox tool-policy filter (dashboard vs CLI divergence)" (runtime contract), `docs/DESIGN.md` § "Sandbox runtime — two-stage tool-policy filter" (architectural rationale).
- **Gateway WebSocket protocol (load-bearing, not JSON-RPC 2.0).** OpenClaw's gateway uses a custom envelope: server sends `{ type: "event", event: "connect.challenge", payload: { nonce } }` on connect → client must reply with `{ type: "req", id, method: "connect", params: { minProtocol: 4, maxProtocol: 4, client: { id: "openclaw-tui" or "openclaw-control-ui", displayName, version, platform, mode }, caps: [], role, scopes, auth: { token } } }` for OpenClaw `2026.6.2` → subsequent RPCs use `{ type: "req"|"res", id, method, params, payload, ok, error }` (NOT `result`/`error` JSON-RPC fields). The `client.id` must be one of the allowed enum values; a free-form id is rejected with code 1008 `invalid connect params`. The operator token lives in `~/.openclaw/openclaw.json` under `gateway.auth.token`; `gateway.controlUi.allowInsecureAuth = true` must be set for token-based auth from local clients. The bug of sending raw `{ jsonrpc: "2.0", method, params, id }` has bit two team members (Person C, Week 1, dashboard `GatewayClient`; Person B, Week 3, `test-self-provisioning.ts` + `test-tuner-e2e.ts`), and the OpenClaw `2026.6.2` upgrade added a second footgun: clients still advertising protocol v3 are rejected with `1002 protocol mismatch expected=4`. The canonical reference implementation is [`scripts/probe-creator-tools.ts:71-173`](../scripts/probe-creator-tools.ts), and the example in [`docs/gateway-rpc.md`](gateway-rpc.md) was updated to v4 on 2026-06-02. Also: `config.get` returns a `ConfigFileSnapshot` wrapper — read agents at `payload.runtimeConfig.agents.list` and use top-level `payload.hash` as the baseHash for `config.patch` (the bare config is at `payload.runtimeConfig`, NOT `payload`).
- **Secrets RPC surface is read-only.** OpenClaw's gateway exposes ONLY `secrets.reload` (no params → `{ ok: true, warningCount }`) and `secrets.resolve` (`{ commandName, targetIds: [knownTargetId] }` — target IDs must be in the registry at `openclaw/src/secrets/target-registry.ts`). There is **no** `secrets.exists`, **no** `secrets.set`, and **no** secret-write RPC. Self-provisioning credentials are written on disk to `~/.openclaw/.env` (dotenv `KEY=VALUE` lines) or via a configured `secrets.providers.<name>.command`; agents call `secrets.reload` afterwards to warm the cache. Documented in `sentura/agents/creator/skills/self-provisioning/SKILL.md` Steps 1, 5, and the Tools list. Discovered 2026-04-26 when the live `T-LIVE-2 secrets.exists` test failed with `unknown method: secrets.exists` — the SKILL.md was authored against an imagined API.
