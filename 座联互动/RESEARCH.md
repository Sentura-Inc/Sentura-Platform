## 1. 结论摘要

### 1.1 首选接入顺序

1. **道旅旅游 DidaTravel**：仍是最适合座联 Phase 1 / Phase 2 的标准化 API 供应商。酒店 API 文档完整、上线流程清楚，并且可复核合作案例较多；但公开文档最完整的是酒店 Booking / Content API，专车和体验活动的实际可订接口仍需商务确认。
2. **深圳捷旅国际 / 房掌柜**：酒店 B2B 分销适配度高，官网直接放出 API 文档入口，且公开协议能看到签字盖章、结算、争议解决等签约形态。适合国内及港澳酒店补充供应。
3. **红色加力**：酒店供应链服务清晰，公开“开发文档”说明了查询、报价、试预订、下单、取消、订单查询、信用额度、状态同步等能力；公开案例显示其服务中移动、鞍钢、国网商旅云及多个酒店集团，企业差旅/公付场景可信度高。
4. **票付通 / 易景通 / 智游宝 / 趣买票**：都是真实景区票务系统或分销生态参与者，适合作为景点门票侧候选；重新计入“合作方资质要求清晰度 + 合作案例”后，优先级建议为 **票付通 > 易景通 > 智游宝 ~= 趣买票**。票付通规模和分销闭环最强；易景通案例公开度较好；智游宝业务真实但文档偏旧；趣买票案例和 API 仍需商务核验。
5. **专车/接送机平台**：按同一 5 维口径和公开网页重新核实后，优先级建议为 **曹操出行 ~= 首汽约车 > 神州专车 > 享道出行**；**T3 出行、阳光出行暂不进入第一批技术接入**。曹操、首汽、神州都有公开开放平台/API/H5 文档；享道有企业出行官网和订单 API 文档片段，需商务确认完整开放平台权限；T3 仅能核实企业版/官网信息，未见公开字段级 API；阳光公开合作更偏车队/租赁公司/聚合运力，未见面向座联这类旅行入口的开放 API，建议排除第一批。
6. **磐河旅行**：开放平台程度较高，覆盖酒店和景点门票，但火车票业务涉及第三方代订/代理，公开站点存在 HTTP 页面，且 12306 官方长期声明未授权第三方售票。新增资质维度后分数下调，只建议把酒店/门票作为补充候选，暂不接火车票和任何涉及身份证、人脸、12306 账号的链路。

### 1.2 不建议作为第一阶段重点

- **泰坦云**：酒店技术/SaaS和供应链能力真实，但公开接口资料不足，更像酒店侧 Switch / 订单管理与分销连接器，适合作为商务合作候选，不适合作为短期可开发 API。
- **龙腾捷旅 / CNBooking**：酒店批发业务真实，产业媒体能核实其 B2B 酒店分销地位；但公开 API 文档弱，合作路径偏人工商务/资源部。
- **分贝通**：企业支出管理和企业商旅真实度高，覆盖酒店和用车，但它是需求侧企业费控平台，不是座联需要的“供应方库存/API”。
- **泰久信息 / 同天下 / 思途CMS**：更偏景区/旅行社系统、ERP、建站中台或软件供应商，不是直接可拿库存的 OTA/供应 API。可作为系统建设参考，不作为第一批供应商。

## 2. 评分口径

总分 100，按“座联要接供应能力”的实际需求评分，不等于公司整体实力评分。

| 维度 | 权重 | 说明 |
|---|---:|---|
| 服务类型匹配 | 20 | 是否覆盖酒店、景点门票、专车/接送机三类；越接近座联旅行服务闭环分越高。 |
| API 开放程度 | 25 | 是否有公开、可读、字段级、流程级 API 文档；是否有测试环境、鉴权方式、示例、回调/订单状态说明。 |
| 业务真实性与合作案例 | 20 | 官网、ICP备案、产业媒体、上市/挂牌、客户/合作方、规模数据、公开工商/招聘/行业资料能否交叉验证；是否能看到具名合作案例。 |
| 签约资质清晰度 | 15 | 平台是否公开或可推导其对合作签约方的准入要求；座联作为分销方/平台方是否容易满足，例如营业执照、旅行社业务经营许可、开发者账号、合同、保证金/预付余额、IP 白名单、测试认证、结算账户、发票主体、数据安全承诺等。 |
| 合规与交付风险 | 20 | 是否涉及高风险资质、第三方票务灰区、个人敏感信息、HTTP 明文、保证金/预付余额不透明、供应链售后不确定。风险越低分越高。 |

通用资质基线：

- 如果座联只做酒店单项分销，通常至少需要公司营业执照、签约主体/发票主体、结算账户、联系人、技术对接人、IP 白名单、测试账号、合同和售后责任约定。
- 如果座联销售“线路/酒景套餐/包价旅游/出境旅游”等旅行社产品，应按《在线旅游经营服务管理暂行规定》《旅行社条例》及 LB/T 030-2014 要求核验旅行社业务经营许可、旅游服务质量保证金、旅行社责任保险、出境游资质等。
- 如果涉及景点门票分销，需确认座联是“分销商/旅行社/OTA 渠道”还是“景区系统客户”；若要代售多景区库存，应要求平台提供分销合同、景区授权链路、退款核销规则、对账结算规则和异常投诉处理 SLA。
- 如果涉及专车/接送机，除供应平台准入外，还要核验车辆/驾驶员营运合规、保险、航班延误与取消规则、乘客信息处理边界。

评级：

- **A：80-100**，优先推进商务/测试账号。
- **B：65-79**，可作为备选或专项接入，需补商务与合同验证。
- **C：50-64**，业务真实但短期 API/供应适配度一般。
- **D：<50**，不建议进入当前接入池，除非客户已有指定合作关系。

## 5. 分平台复核

### 5.1 道旅旅游 / DidaTravel

**服务类型**

- 酒店：明确核心品类，官网称超百万家酒店资源，Dida API 页面主推酒店与机票销售。
- 景点门票：官网产品线含 `Dida Experience`，首页描述“旅游与体验活动”。
- 专车/接送：官网产品线含 `Dida Go`，首页描述“地面接送服务”。

**API 开放程度**

- 酒店 API 文档完整。公开文档包括：
  - Booking API `PriceSearch`：价格查询。
  - `PriceConfirm`：预订前确认价格，`PreBook=true` 返回 `ReferenceNo`。
  - `HotelBookingConfirm`：创建订单，需要使用 `PriceConfirm` 返回的 reference。
  - `HotelBookingSearch`：订单查询，并明确只有状态 `2/3/4` 是最终状态。
  - Content API v2：`/api/v1/region/countries`、`/api/v1/region/destinations`、`/api/v1/hotel/list`、`/api/v1/hotel/details`，Basic Auth，JSON 返回，QPS 限制明确。
- 需要注意：公开文档中最完整的是酒店；`Dida Go` 和 `Dida Experience` 的可订 API 需要通过商务/账号进一步确认。

**真实性与靠谱度**

- 官网、API 文档、ICP备案、产品线、合作伙伴评价、招聘/投资者链接都能互相印证。
- 官网显示 2026 年仍在发布合作新闻，业务持续性较强。
- 技术文档质量在本次清单中最好，适合直接做 Sitlink 的模拟和未来真实接入。

**风险**

- 正式调用需要 API 买家账号；测试账号数据有限。
- 国际酒店涉及取消政策、供应商多语言、HCN 返回时点、OnRequest 等售后复杂性。
- 专车/体验活动不能仅凭官网产品线直接认定已有可用 API，需要拿到具体文档。

**评分：92 / A**

**建议**

- 立即推进座联主体注册和商务沟通。
- 技术侧优先按酒店 API 做真实适配层；专车/体验活动先问商务索取文档、测试账号和 SLA。

**服务类型**

- 景点门票：官网标题/导航出现“门票预订”，但本轮重点和可核实 API 文档集中在酒店。

- 接入流程仍需注册、签约、测试账号、IP 授权、联调和正式环境开通。

**真实性与靠谱度**

- 官网、ICP备案、合作伙伴展示、7x24 客服、行业资料均能支持其酒店 B2B 分销真实性。

**风险**

**评分：87 / A**

**建议**

## 8. 推荐的下一步商务与技术动作

### 8.1 酒店

1. 道旅：申请 API 买家账号和测试账号；确认酒店、Dida Go、Dida Experience 三条线的正式接口范围。
2. 捷旅：注册房掌柜分销商，索取最新酒店 API 文档、测试账号、联调案例。
3. 红色加力：联系商务索取完整开发文档、测试/生产地址、信用额度与公付结算规则。
4. 签约资料预备：营业执照、合同章/授权书、旅行社业务经营许可证或平台经营说明、开票资料、结算账户、技术联系人、IP 白名单、售后联系人、数据安全承诺。

### 8.2 景点门票

1. 票付通：申请开发者/旅游云账号，确认座联可作为分销商还是只能作为景区系统客户。
2. 易景通：索取 API 文档样章、可接景区列表、OTA/旅行社分销案例，并确认是否支持统一库存池而不是单景区项目制。
3. 智游宝、趣买票：先商务确认是否开放给外部分销方；若只能在平台内交易或只能服务景区系统客户，降低优先级。
4. 签约资料预备：营业执照、旅行社/OTA/分销资质、景区授权链路、门票退款/核销/改期规则、对账结算周期、保证金/预付余额安排、投诉和异常入园 SLA。

### 8.3 专车/接送机

1. 曹操：优先申请开放平台开发者账号和沙箱应用，确认接送机、预约用车、企业用车、H5 免登、订单状态回调和正式应用授信/充值流程。
2. 首汽：索取正式商务准入要求和生产权限流程，重点确认接送机、会务包车、机场/高铁站覆盖城市、取消费/等待费规则。
3. 神州：并行评估 H5 接入与 API 接入；H5 用于快速 Demo，API 用于后续深度订单控制。
4. 享道：索取完整 API 文档、沙箱、正式域名和企业版合作资料；若只能企业后台/App 使用或只能租赁公司/运力合作，降为补充或排除。
5. T3：先商务确认是否存在外部分销 API/H5 模式；没有公开文档前不进入第一批开发。
6. 阳光：当前公开路径更偏租赁公司/车队/聚合运力，不建议作为座联直连接口供应商；除非对方明确提供旅行入口/API 买方合同，否则排除。
7. 道旅：同时问清 Dida Go 是否有接送机/包车 API、覆盖城市、取消规则、司机/车辆信息回传、航班延误处理，作为国际/跨境供应补充。
8. 签约资料预备：企业营业执照、合同章/授权书、企业账户、充值/授信安排、技术回调域名/IP、数据安全协议、车辆/司机营运合规证明、保险责任、乘客信息处理协议、航班延误等待规则、取消费规则、紧急客服 SLA。**若平台要求座联经营范围含汽车租赁、持有营运车辆、司机管理能力或网约车运输证资源，按运力加盟处理，原则上排除。**
